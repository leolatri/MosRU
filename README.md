# Реестр нарушений

WEB-приложение для управления данными нарушений из XLSX-файла. Проект объединяет React-клиент, NestJS API и PostgreSQL в одном репозитории и запускается через Docker Compose.

## Возможности

- регистрация и вход с JWT-авторизацией;
- защищённые API-эндпоинты;
- просмотр нарушений с серверной пагинацией, фильтрацией и `ILIKE`-поиском;
- создание, редактирование и удаление нарушений в интерфейсе;
- CRUD API для справочных сущностей;
- импорт XLSX с проверкой структуры, нормализацией и атомарным UPSERT;
- экспорт отфильтрованных данных в XLSX;
- Swagger-документация;
- дашборд с четырьмя визуализациями Nivo и общими с таблицей фильтрами;
- миграции базы данных на чистом SQL без ORM.

## Стек

- Frontend: React 19, TypeScript, Ant Design, Nivo, Vite;
- Backend: Node.js 22, NestJS, TypeScript;
- Database: PostgreSQL 16, `pg`, `node-pg-migrate`;
- Infrastructure: Docker Compose, Nginx;
- Auth: JWT, bcrypt.

## Быстрый запуск через Docker Compose

Требуются Docker и Docker Compose. Все команды выполняются из корня репозитория.

```bash
cp .env.example .env
docker compose up --build
```

После запуска доступны:

- интерфейс: <http://localhost:8080>;
- API: <http://localhost:3000/api>;
- Swagger: <http://localhost:3000/docs>;
- PostgreSQL с хоста: `localhost:5433`.

Для запуска в фоне и просмотра состояния:

```bash
docker compose up --build -d
docker compose ps
```

Логи:

```bash
docker compose logs -f backend
docker compose logs -f db
```

Остановка без удаления данных:

```bash
docker compose down
```

Полный сброс:

```bash
docker compose down -v
docker compose up --build
```

Команда с `-v` удаляет Docker volume и все данные PostgreSQL.

## Переменные окружения

`.env` не хранится в Git. Перед запуском нужно скопировать `.env.example`.

| Переменная | Назначение |
| --- | --- |
| `POSTGRES_DB` | имя базы данных |
| `POSTGRES_USER` | пользователь PostgreSQL |
| `POSTGRES_PASSWORD` | пароль PostgreSQL |
| `JWT_SECRET` | секрет подписи JWT |
| `DATABASE_URL` | подключение локального backend к PostgreSQL через порт `5433` |

Внутри Docker backend подключается к `db:5432`; Compose передаёт это значение вместо локального `DATABASE_URL`.

## Документация к проекту

### Тестовые учётные данные

На чистой базе пользователь ещё не существует. Для воспроизводимого тестирования сначала зарегистрируйте эти данные, затем используйте их для входа:

```text
Email: reviewer@example.com
Пароль: Reviewer123!
```

Регистрация доступна на <http://localhost:8080/registration> и через `POST /api/auth/register` в Swagger.

### Миграции БД

Compose-сервис `migrations` запускается после перехода PostgreSQL в состояние `healthy`. Backend стартует только после успешного применения миграций.

`node-pg-migrate` выполняет SQL из `backend/migrations` и записывает историю в таблицу `pgmigrations`. Секция `-- Up Migration` применяется, `-- Down Migration` используется для отката.

Применить миграции вручную:

```bash
docker compose run --rm migrations npm run migrate:up
```

Откатить последнюю:

```bash
docker compose run --rm migrations npm run migrate:down
```

После публикации миграцию не следует редактировать: изменение схемы оформляется новым файлом с последующим номером.

### Ручное тестирование интерфейса

1. Запустить проект и открыть страницу регистрации.
2. Зарегистрировать тестовые данные и войти.
3. Загрузить предоставленный исходный XLSX кнопкой «Импорт XLSX».
4. Проверить строки, общее количество, пагинацию, поиск и фильтры.
5. Создать нарушение, отредактировать его и удалить с подтверждением.
6. Применить фильтр, экспортировать XLSX и проверить содержимое файла.
7. Открыть `/dashboard`, изменить фильтры и проверить пересчёт итога и четырёх графиков.
8. Импортировать файл с неправильным расширением или заголовком и проверить сообщение об ошибке.

### Ручное тестирование API через Swagger

1. Открыть <http://localhost:3000/docs>.
2. Выполнить `POST /api/auth/register`. Если пользователь уже существует, перейти к входу.
3. Выполнить `POST /api/auth/login` и скопировать `accessToken`.
4. Нажать **Authorize** и вставить токен без слова `Bearer`.
5. Проверить `GET /api/violations` и поля `items`, `meta`.
6. Проверить `page`, `limit`, `search`, фильтры, `sortBy` и `sortOrder`.
7. Проверить GET, POST, PATCH и DELETE справочников. Дубликат должен вернуть `409`, удаление используемой записи — конфликт.
8. Проверить POST, GET, PUT и DELETE нарушений.
9. Отправить XLSX через `POST /api/imports/xlsx` как `multipart/form-data`.
10. Скачать `GET /api/violations/export/xlsx` с фильтрами.
11. Удалить или испортить токен и получить `401 Unauthorized`.

## Защита архитектурных решений

### Схема и нормализация

`violations` хранит факты о нарушениях. Повторяющиеся значения вынесены в справочники:

- `administrative_okrugs` — коды округов;
- `districts` — районы и принадлежность округу;
- `object_categories` — категории объектов;
- `problem_topics` — проблемные темы;
- `response_statuses` — статусы ответа;
- `category_problem_topics` — допустимые пары категорий и тем;
- `users` — учётные записи и хеши паролей.

Схема соответствует примерно третьей нормальной форме: каждый справочный факт хранится один раз, неключевые атрибуты зависят от ключа своей таблицы, связи защищены внешними ключами. Это уменьшает дублирование XLSX и аномалии обновления.

`district_id` и `response_deadline` допускают `NULL`: отсутствие значения отличается от пустой строки. Обязательные строки защищены `NOT NULL` и `CHECK`. Согласованность категории и темы обеспечивает составной внешний ключ.

### Рассмотренные альтернативы

- Одна широкая таблица отклонена из-за повторения названий и аномалий обновления.
- `jsonb` упростил бы сохранение исходной строки, но ухудшил бы типизацию, внешние ключи и аналитику.
- Отдельная сущность объекта не выделена: это свободный текст без надёжного бизнес-ключа.
- Искусственный ID для `category_problem_topics` не нужен: пара двух внешних ключей является естественным ключом.
- ORM не используется по условию задания; явный SQL даёт контроль над ограничениями, UPSERT и планами.

### UPSERT с учётом связей

Импорт атомарный. Сначала весь файл парсится и валидируется. При любой ошибке запись в БД не начинается. Затем открывается одна транзакция:

1. UPSERT категории, темы и статуса;
2. UPSERT округа и района, если они указаны;
3. создание связи категории и темы;
4. UPSERT нарушения.

ID справочников возвращаются через `RETURNING id` и кэшируются в `Map`. Конфликт нарушения определяется по `source_message_id`; остальные поля обновляются. `application_number` тоже уникален, поэтому противоречие с другой записью отменяет транзакцию.

### Динамический SQL и SQL-инъекции

Фильтры, поиск и пагинация передаются параметрами `$1`, `$2` и т.д. Поиск строится как `ILIKE '%' || $n || '%'`, поэтому значение пользователя не становится SQL-синтаксисом.

Имена столбцов нельзя параметризовать. `sortBy` сопоставляется с whitelist `SORT_COLUMNS`, а направление выбирается только между `ASC` и `DESC`. Готовый SQL с frontend не принимается.

Один `buildViolationQuery()` используется списком, экспортом и дашбордом, поэтому фильтры имеют одинаковую семантику.

### Индексы

- уникальные B-tree индексы поддерживают `source_message_id`, `application_number`, справочники и регистронезависимый email;
- индексы дат помогают диапазонным условиям и сортировке;
- индексы `district_id` и `response_status_id` ускоряют фильтры и соединения;
- составной индекс категории и темы соответствует внешнему ключу и совместной фильтрации.

PostgreSQL выбирает индексное или последовательное сканирование по статистике. B-tree не ускоряет шаблон `%строка%`; при росте нужен `pg_trgm` и GIN/GiST. Фактические планы проверяются через `EXPLAIN (ANALYZE, BUFFERS)`.

### Безопасность

- bcrypt с cost factor 12;
- JWT действует один час;
- глобальный guard защищает всё, кроме регистрации и входа;
- глобальный `ValidationPipe` отклоняет неизвестные свойства;
- SQL-значения параметризованы;
- ограничения повторно проверяются PostgreSQL.

### Компромиссы и ограничения

- XLSX обрабатывается в памяти, лимит файла — 10 МБ;
- последовательный UPSERT в одной транзакции ограничивает скорость больших импортов;
- дашборд выполняет несколько агрегирующих запросов при смене фильтров;
- JWT хранится в `localStorage`; для production предпочтительнее HttpOnly cookie и refresh token;
- автоматические тесты пока не добавлены;
- API поддерживает сортировку, но выбор сортировки в Ant Design Table пока не подключён;
- backend возвращает ошибки импорта `{ row, field, message }`, но frontend пока показывает только общее уведомление;
- CRUD справочников проверяется через Swagger, frontend предоставляет CRUD нарушений.

## Масштабирование до миллионов строк

1. Измерить запросы через `EXPLAIN ANALYZE` и `pg_stat_statements`.
2. Добавить `pg_trgm`/GIN для подстрочного поиска.
3. Заменить глубокую offset-пагинацию на keyset pagination.
4. Читать XLSX потоково и выполнять UPSERT пакетами.
5. Перенести импорт в очередь BullMQ/RabbitMQ с прогрессом и идемпотентностью.
6. Хранить файлы в объектном хранилище.
7. Кэшировать справочники и агрегаты в Redis, использовать материализованные представления.
8. Рассмотреть партиционирование по дате только после анализа запросов.
9. Для тяжёлой аналитики реплицировать данные в ClickHouse.
10. Добавить read-replica и наблюдаемость.
